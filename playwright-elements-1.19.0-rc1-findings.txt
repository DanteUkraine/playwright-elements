================================================================================
01  BLOCKER — circular require crashes 4 of 9 entry points
================================================================================

WHAT
  lib/web.element.js:17 does `const index_1 = require("./index")`, and
  lib/index.js requires ./web.element (line 9) and ./playwright.test.fixtures
  (line 20). lib/playwright.test.fixtures.js also requires ./index. So there
  are two cycles:

      index.js -> web.element.js -> index.js
      index.js -> playwright.test.fixtures.js -> index.js

  index.js survives its own cycle only because it publishes lazy getters
  (Object.defineProperty(..., { get })) and happens to define the WebElement
  getter at line 10, before requiring the fixtures at line 20. That ordering is
  load-bearing and undocumented.

  If any module inside the cycle is the FIRST one loaded, the getter has not
  been installed yet, and the fixtures module dereferences `undefined`.

EVIDENCE
  $ node -e "require('playwright-elements/lib/web.element')"

  /node_modules/playwright-elements/lib/playwright.test.fixtures.js:8
  index_1.WebElement.setExpectProvider({
                     ^
  TypeError: Cannot read properties of undefined (reading 'setExpectProvider')
      at Object.<anonymous> (lib/playwright.test.fixtures.js:8:20)
      at Object.<anonymous> (lib/index.js:20:34)

  Every entry point, each loaded first in a fresh process:

    lib/index                     OK
    lib/web.element               CRASH
    lib/browser                   OK
    lib/test.support              CRASH
    lib/testIds/builder           OK
    lib/testIds/selectors         CRASH
    lib/testIds/index             CRASH
    lib/page.object.builder       OK
    lib/playwright.test.fixtures  OK

WHY IT MATTERS
  - It contradicts the package's own design claim. test.support.d.ts:63 says
    "The WebElement class itself has no dependency on @playwright/test."
    The cycle makes that false in practice: loading web.element pulls index,
    which pulls playwright.test.fixtures, which requires @playwright/test.
  - lib/testIds/index is one of the crashing paths. That is the natural deep
    import for anyone trying to use the testIds module without the browser
    stack — see finding 06.
  - CommonJS tolerates the cycle by accident of ordering. Bundlers and ESM
    consumers do not guarantee that ordering. This is the class of bug that
    shows up as "works in my repo, crashes in yours".

PROPOSED FIX
  web.element.js needs exactly one thing from ./index, and it lives in
  ./browser. Verified — the only uses are:

    lib/web.element.js:46   index_1.BrowserInstance.currentPage.locator(...)
    lib/web.element.js:95   index_1.BrowserInstance.currentPage
    lib/web.element.js:387  index_1.BrowserInstance.currentPage.addLocatorHandler
    lib/web.element.js:390  index_1.BrowserInstance.currentPage.removeLocatorHandler
    lib/web.element.js:643  index_1.BrowserInstance.isContextMobile

  In the source, change the import in web.element.ts from

      import { BrowserInstance } from './index';
  to
      import { BrowserInstance } from './browser';

  That removes cycle 1 outright. Do the same in playwright.test.fixtures.ts,
  which needs BrowserInstance, usePage and WebElement:

      import { BrowserInstance, usePage } from './browser';
      import { WebElement } from './web.element';

  That removes cycle 2. After both, index.ts is a pure barrel that nothing
  inside the package imports, which is the invariant worth keeping.

  Recommended guard so it cannot come back: a CI step that loads every
  published entry point first, in its own process.

      for f in $(cd lib && find . -name '*.js' ! -name '*.cli.js'); do
        node -e "require('./lib/${f}')" || { echo "FAILS FIRST: $f"; exit 1; }
      done

  A lint rule (import/no-cycle, or eslint-plugin-import's no-self-import plus
  no-cycle with maxDepth 3) covers the source side.

02  BLOCKER — `implicitNavigation` is declared in the .d.ts but never defined
================================================================================

WHAT
  lib/playwright.test.fixtures.d.ts:9 declares a fixture named
  `implicitNavigation: void` in the exported TestType. lib/playwright.test.
  fixtures.js defines only `goto`, `initBrowserInstance` and `usePage` — the
  string "implicitNavigation" does not appear in the .js at all.

EVIDENCE
  $ grep -c implicitNavigation lib/playwright.test.fixtures.d.ts   ->  1
  $ grep -c implicitNavigation lib/playwright.test.fixtures.js     ->  0

  A test that destructures it type-checks cleanly:

      import { test } from "playwright-elements";
      test("x", async ({ implicitNavigation }) => { void implicitNavigation; });

  `tsc --noEmit` reports nothing. Playwright then refuses the file:

      Test has unknown parameter "implicitNavigation".
         at probe.test.ts:27
      > 27 | test("a fixture the .d.ts declares...", async ({ implicitNavigation })

WHY IT MATTERS
  This is not a failing test, it is a COLLECTION error: Playwright aborts the
  entire spec file, so every other test in it disappears from the run. And the
  compiler actively points the user at it — autocomplete offers the fixture,
  tsc approves it, the runner rejects it. That is the worst possible split
  between the two tools a Playwright user trusts.

PROPOSED FIX
  Decide which of the two it is:

  (a) It is a real feature that was dropped. Then define it, and give it a
      behaviour worth a name — presumably navigating to a baseURL-relative
      path before the test body.

  (b) It is a leftover. Then delete it from the declaration. Because the
      published .d.ts is generated from the source, the stale entry means the
      source still declares it in the fixtures generic; remove it there.

  Either way, the structural fix is that the .d.ts should be EMITTED from the
  same object literal that defines the fixtures, so the two cannot disagree.
  Today `test` is typed by inference over `test_1.test.extend({...})`, which
  would already have caught this — so the declaration was likely widened by
  hand somewhere. Removing the hand-written widening is the durable fix.

  Guard: one type-level test that asserts the fixture NAMES of the exported
  test equal the keys actually passed to extend(). expect-type is already a
  devDependency:

      import { expectTypeOf } from 'expect-type';
      // fails if the declared fixture set drifts from the defined one
      expectTypeOf<Parameters<Parameters<typeof test>[1]>[0]>()
        .toHaveProperty('goto');

  Plus one runtime test that destructures every documented fixture, which
  would have failed loudly at collection.

03  HIGH — expect() and softExpect() return `any`
================================================================================

WHAT
  lib/web.element.d.ts:116   expect(message?: string): any;
  lib/web.element.d.ts:127   softExpect(message?: string): any;

  In 1.18.2 these were typed:

      lib/web.element.d.ts:78   expect(message?: string): LocatorExpect;
      where  type LocatorExpect = ReturnType<typeof _expect<Locator>>;

  So the RC removes matcher type-checking from every component assertion.

EVIDENCE
  Compiled inside a real project (tsconfig strict, TS 5.x):

      import { $ } from "playwright-elements";
      const a = $("#x");
      await a.expect().toBeVisibleeee();   // no error
      await a.softExpect().nope();         // no error

  `tsc --noEmit` reports NOTHING for either line. On 1.18.2 both are errors.

WHY IT MATTERS
  The suite this was tested in has 1107 tests and treats `tsc` as the first
  gate — a renamed part or a mistyped matcher is supposed to fail the build,
  not time out in Chromium 40 minutes later. Losing matcher typing means:
    - typos reach CI and surface as a runtime TypeError inside a test body;
    - matcher ARGUMENTS are unchecked, so toHaveCount("3") compiles;
    - `.not` chains are unchecked;
    - IDE autocomplete on `el.expect().` returns nothing at all, which is a
      visible downgrade for anyone moving from 1.18.2.

  `WebElementExpect` exists in test.support.d.ts and is exported from the
  index, but nothing uses it as a return type (see finding 14), so the
  intention is clearly there and only the wiring is missing.

PROPOSED FIX
  Do NOT type it as `WebElementExpect` — that hand-maintained subset omits 22
  matchers this suite uses (finding 14). Make the provider generic instead, so
  the real Playwright matcher set flows through and the class keeps having no
  compile-time dependency on @playwright/test:

      // web.element.ts
      export interface ExpectProvider<E = unknown, S = E> {
        expect: (locator: Locator, message?: string) => E;
        softExpect: (locator: Locator, message?: string) => S;
      }

      // one module-level slot, typed by whatever was registered
      let _expectProvider: ExpectProvider<any, any> | undefined;

      export declare class WebElement {
        static setExpectProvider<E, S>(p: ExpectProvider<E, S>): void;
        expect(message?: string): ExpectReturn;
        softExpect(message?: string): SoftExpectReturn;
      }

  The clean way to carry E/S to the instance method without making WebElement
  itself generic (which would be a breaking change for every consumer) is a
  declaration-merging seam the test-side package augments:

      // web.element.ts — the default, when nobody registers anything
      export interface WebElementAssertions {
        expect: unknown;
        softExpect: unknown;
      }
      type ExpectReturn = WebElementAssertions['expect'];
      type SoftExpectReturn = WebElementAssertions['softExpect'];

      // playwright.test.fixtures.ts — the Playwright binding
      import { expect as pwExpect } from '@playwright/test';
      declare module './web.element' {
        interface WebElementAssertions {
          expect: ReturnType<typeof pwExpect<Locator>>;
          softExpect: ReturnType<typeof pwExpect<Locator>>;
        }
      }

  Importing `test` from the package — which every Playwright user already does
  and which already calls setExpectProvider — then also fixes the type, with
  no API change and no work for the consumer. A non-Playwright runner that
  registers its own provider augments the same interface.

  If declaration merging is more machinery than wanted, the minimal fix that
  still restores 1.18.2 behaviour is to re-declare the 1.18.2 alias:

      import type { Expect } from '@playwright/test';
      declare const _expect: Expect<{}>;
      type LocatorExpect = ReturnType<typeof _expect<Locator>>;
      expect(message?: string): LocatorExpect;

  This reintroduces a type-only import of @playwright/test into web.element.
  Type-only costs nothing at runtime and does not undo the provider pattern.

  Guard: a compile-fail test. expect-type is already a devDependency:

      // @ts-expect-error a misspelled matcher must not compile
      await $('#x').expect().toBeVisibleeee();

04  HIGH — $byTestIdPrefix emits an unquoted attribute value
================================================================================

WHAT
  lib/testIds/selectors.js:81

      return $(`[data-testid^=${factory.prefix}]`);

  Every sibling selector quotes its value. Only the prefix one does not:

      $byTestId          ->  [data-testid="..."]     quoted   OK
      $byTestIdPrefix    ->  [data-testid^=...]      UNQUOTED
      $byTestIdContaining->  [data-testid*="..."]    quoted   OK
      $byTestIdEndingWith->  [data-testid$="..."]    quoted   OK

  An unquoted CSS attribute value must be a valid CSS identifier. A prefix
  containing `.`, `:`, `/`, `#`, `%`, a leading digit, or whitespace is not.

EVIDENCE
  A prefix with a dot — an extremely common shape for namespaced ids, and the
  exact shape the README's own `sid<'login.username'>` kind phrases suggest:

      await page.setContent(`<div data-testid="section.hero-1">A</div>`);
      const sel = $byTestIdPrefix(factory("section.hero")).selector;
      // "[data-testid^=section.hero]"
      await page.locator(sel).count();

      Error: locator.count: SyntaxError: Failed to execute 'querySelectorAll'
      on 'Document': '[data-testid^=section.hero]' is not a valid selector.

WHY IT MATTERS
  It is a hard throw, not a mismatch, and it only reproduces for some ids — so
  it lands as an intermittent-looking failure that depends on the naming
  convention a given team picked. A team using dotted namespaces cannot use
  $byTestIdPrefix at all.

PROPOSED FIX
  Quote it like the other three, and escape the value rather than trusting it:

      const cssString = (value: string): string =>
        typeof CSS !== 'undefined' && CSS.escape
          ? `"${value.replace(/["\\]/g, '\\$&')}"`
          : `"${value.replace(/["\\]/g, '\\$&')}"`;

      return $(`[data-testid^=${cssString(factory.prefix + '-')}]`);

  (The `+ '-'` is finding 05.) Escaping `"` and `\` inside the quoted form is
  enough for CSS attribute-value syntax and needs no CSS.escape, so it works
  in Node as well as in the page.

  Apply the same escaping to $byTestId, $byTestIdContaining and
  $byTestIdEndingWith. They are quoted so they do not throw, but an id
  containing a double quote silently produces a selector that matches the
  wrong thing, which is worse than throwing.

  Guard: table-driven unit test over ids designed to break CSS —
  `a.b`, `a:b`, `1a`, `a b`, `a"b`, `a\\b`, `a/b`, `a#b`, `a%b` — asserting
  each selector both parses and matches exactly the intended node.

================================================================================
05  HIGH — $byTestIdPrefix has no delimiter, so it matches sibling ids
================================================================================

WHAT
  IdFactory.prefix is documented (builder.d.ts:97) as "Static portion of the
  ID, with NO trailing `-`", and `factory` produces ids as join([prefix, key])
  — i.e. `${prefix}-${key}`. But $byTestIdPrefix selects on the bare prefix,
  so it also matches any OTHER registered id that merely begins with the same
  characters.

EVIDENCE
  Real collision from the suite under migration. Both of these are stamped in
  the same document by the same page:

      <section data-testid="idx-consents">          <- a static container id
        <div data-testid="idx-consent-acme">A</div> <- factory('idx-consent')
        <div data-testid="idx-consent-globex">B</div>
      </section>

      $byTestIdPrefix(factory("idx-consent")).selector
        -> "[data-testid^=idx-consent]"

      matched count      : 3        (expected 2)
      first match testid : idx-consents

  So a count assertion is off by one, and `.first()` returns the WRAPPER
  instead of the first record. Both failures are quiet: the count is merely
  wrong, and `.first()` on the wrapper still resolves, still is visible, and
  still has text — so assertions on it can pass.

  The suite under migration hit exactly this and works around it by appending
  the delimiter in its own selector builder, with a regression test on the
  boundary.

WHY IT MATTERS
  Prefix selection exists to address "a collection of dynamically-generated
  ids". Silently including a sibling breaks the only thing it is for, and the
  broken form still passes shallow assertions.

PROPOSED FIX
  Select on the prefix PLUS the delimiter the factory itself inserts:

      return $(`[data-testid^="${escape(factory.prefix)}-"]`);

  The delimiter is not a convention here, it is what `join` already emits, so
  this makes the read side agree with the write side by construction.

  This is a behaviour change for anyone relying on today's loose matching.
  Given it is an RC of a version that introduces the module, changing it now
  is much cheaper than after release. If backwards compatibility is wanted,
  add an option rather than keeping the loose default:

      $byTestIdPrefix(factory, { exactSegment: false })   // opt OUT

  Guard: a test asserting `factory('idx-consent')` does NOT match a static
  `sid('idx-consents')` in the same document — i.e. the exact case above.

  Related: `bareFactory()` has `prefix: ''` and $byTestIdPrefix throws at
  RUNTIME for it (selectors.js:78). That is knowable at compile time. Give
  bareFactory a distinct type so passing it is a tsc error:

      export interface BareIdFactory<K extends string = string> {
        (key: string | number): TestId<K>;
        readonly prefix: '';
      }
      export declare const bareFactory: <K extends string = string>()
        => BareIdFactory<K>;
      // and narrow $byTestIdPrefix to reject prefix: ''
      export declare const $byTestIdPrefix: <K extends string>(
        factory: IdFactory<K> & { prefix: '' extends IdFactory<K>['prefix']
          ? never : string }
      ) => WebElement;

  A simpler equivalent: type the parameter as `IdFactory<K>` where `prefix`
  is declared `string & {}` on factory() and `''` on bareFactory(), and have
  $byTestIdPrefix accept only the former.

06  HIGH — no dependency-free entry point for the testIds module
================================================================================

WHAT
  The README recommends importing testIdProps into application React code:

      components/MyComponent.tsx
      import { testIdProps } from 'playwright-elements';
      import { ids } from '../testIds';
      export function MyComponent() {
        return <input {...testIdProps(ids.login.usernameInput)} />;
      }

  There is no way to do that without loading the whole browser stack, because
  the root barrel requires ./browser, ./web.element and
  ./playwright.test.fixtures.

EVIDENCE
  $ node -e "
      const before = new Set(Object.keys(require.cache));
      require('playwright-elements');
      const added = Object.keys(require.cache).filter(k => !before.has(k));
      ...
    "
    playwright-core files loaded : 6
    @playwright/test files loaded: 1
    total modules pulled in      : 33

  And the deep import that would avoid it is one of the four that crash
  (finding 01):

    lib/testIds/index      CRASH
    lib/testIds/selectors  CRASH
    lib/testIds/builder    OK      <- the only working one, and it is
                                      an unversioned internal path

WHY IT MATTERS
  Following the README makes a test library a PRODUCTION dependency of the
  application. Concretely, in the repo under migration:
    - `npm ci --omit=dev` on the deploy target would fail to resolve it, so
      the package would have to move from devDependencies to dependencies;
    - a Next.js production bundle would carry playwright-core's module graph;
    - the peerDependencies on @playwright/test and playwright-core would have
      to be satisfied in production too.

  That is why this suite kept its own copy of sid/factory/testIdProps in the
  application and used only the SELECTOR half ($byTestId) from the package.
  Nobody should have to make that call — and the duplicate is exactly what the
  testIds module is meant to eliminate.

PROPOSED FIX
  Publish testIds/builder as a supported, dependency-free subpath, and add an
  exports map so it is a contract rather than an internal path:

      // package.json
      "type": "commonjs",
      "main": "lib/index.js",
      "types": "lib/index.d.ts",
      "exports": {
        ".": { "types": "./lib/index.d.ts", "default": "./lib/index.js" },
        "./testids": {
          "types": "./lib/testIds/builder.d.ts",
          "default": "./lib/testIds/builder.js"
        },
        "./package.json": "./package.json"
      }

  builder.js already requires nothing, so `playwright-elements/testids` costs
  the consumer zero runtime dependencies and can live in application code:

      import { testIdProps, sid, factory } from 'playwright-elements/testids';

  Keep the root re-export for test-side convenience. Two notes on doing this:

    - Do NOT point the subpath at lib/testIds/index.js: that re-exports
      ./selectors, which requires ../web.element and drags playwright-core
      back in (and crashes today, per finding 01). The split has to be
      builder = pure, selectors = test-side.
    - Add a CI assertion that the subpath stays pure, because it is the kind
      of thing one convenience import undoes:

          node -e "
            const before = Object.keys(require.cache).length;
            require('./lib/testIds/builder');
            const n = Object.keys(require.cache).length - before;
            if (n !== 1) { console.error('impure subpath:', n, 'modules'); process.exit(1); }
          "

  Then update the README's MyComponent.tsx example to import from the subpath,
  since that example is the one people will copy.

================================================================================
07  MEDIUM — useExpect() lost its parameter (breaking change, minor bump)
================================================================================

WHAT
  1.18.2  lib/web.element.d.ts:77   static useExpect<T>(expect: Expect<T>): void;
  1.19rc1 lib/web.element.d.ts:107  static useExpect(): void;

  Any consumer who wrote `WebElement.useExpect(expect)` — which is what the
  1.18.2 signature asked for — now fails to compile with TS2554 (expected 0
  arguments, got 1) on a minor version upgrade.

  Body in both versions is a no-op. In 1.18.2 it was `{ expect; }`; in the RC
  it is an empty block with a comment.

WHY IT MATTERS
  The upgrade path breaks silently at compile time for exactly the users who
  did the thing the old type told them to do. And because the old function
  never worked, they will have written it, seen it not help, and moved on —
  so the compile error arrives with no memory of why the call exists.

PROPOSED FIX
  Keep it source-compatible for one more major cycle and make it actually
  work, since the machinery now exists:

      /** @deprecated Use setExpectProvider(). Kept working for 1.x. */
      static useExpect(expect?: { (locator: unknown, message?: string): unknown;
                                  soft: (locator: unknown, message?: string) => unknown }): void {
        if (expect) {
          WebElement.setExpectProvider({ expect, softExpect: expect.soft });
          return;
        }
        // no argument: previous behaviour, nothing to configure
      }

  An optional parameter is not a breaking change, and a deprecated function
  that does what its name says is strictly better than one that silently does
  nothing. Then remove it in 2.0.

  If it must stay a no-op, at least make the no-op loud in dev:

      static useExpect(): void {
        console.warn('[playwright-elements] useExpect() does nothing. ' +
                     'Use WebElement.setExpectProvider({ expect, softExpect: expect.soft }).');
      }

08  MEDIUM — extendWebElementWithAssertions() is an empty exported function
================================================================================

WHAT
  lib/test.support.js:15

      function extendWebElementWithAssertions() {
          // This function exists to explicitly load assertion support
          // The actual extension happens through the WebElement class itself
      }

  It is exported from the package index (index.d.ts:10) with a docstring that
  describes behaviour ("Extension methods for WebElement to support assertion
  chaining"). It does nothing at all.

WHY IT MATTERS
  This is the same trap useExpect() was: public, documented, named for an
  effect, and inert. Someone will call it, get an unconfigured provider error
  anyway, and have no way to tell the two failures apart.

  It also cannot serve its stated purpose. "Exists to explicitly load
  assertion support" would only work as an import side effect, and the side
  effect that actually configures the provider is in
  playwright.test.fixtures.js, not here.

PROPOSED FIX
  Delete it from the public surface. If a "load the support module for its
  side effect" hook is genuinely wanted, make it the side effect:

      // test.support.ts — top level, not inside a function
      configureWebElementExpect();

  ...and then document `import 'playwright-elements/test-support'` as the
  hook. But note that for Playwright Test users this is already unnecessary
  (finding 09), so the simplest correct answer is to remove it and let
  setExpectProvider / configureWebElementExpect be the only two names.

================================================================================
09  MEDIUM — configureWebElementExpect() docs say it "must be called"
================================================================================

WHAT
  lib/test.support.d.ts:58-70

      "Configures WebElement to use Playwright's expect for assertion
       chaining. This must be called in your test setup before using
       element.expect() or element.softExpect()."

  For Playwright Test users this is false. lib/playwright.test.fixtures.js:8
  already runs, at module load:

      WebElement.setExpectProvider({ expect, softExpect: expect.soft });

  and that module is loaded by the index barrel, so merely importing anything
  from 'playwright-elements' configures the provider. The README says so
  correctly ("expect() and softExpect() work automatically ... due to
  automatic provider configuration"), so the two disagree.

WHY IT MATTERS
  Following the docstring is harmless but pointless, and it teaches users that
  there is required setup where there is none — which then makes the real
  requirement (a non-Playwright runner must register a provider) invisible,
  because everyone learned to sprinkle the call everywhere.

PROPOSED FIX
  Rewrite the docstring to say when it IS needed:

      /**

10  MEDIUM — two sibling methods in one .with() cannot call each other
================================================================================

WHAT
  NestedElements (web.element.d.ts:6) rewrites each method's `this` to
  `T & Omit<NestedElements<T, A>, K>` — the component MINUS that method — and
  discards any `this` annotation the author wrote. So for two methods declared
  together, each one's available `this` is missing itself while the other one
  DEMANDS a `this` that has it. The two are mutually unassignable.

EVIDENCE
      export const form = $("#f").with({
        input: $("input"),
        field(name: string) { return this.$(`[name="${name}"]`); },
        async fill2(n: string) { await this.field(n).fill("v"); },
      });

  tsc:
      error TS2684: The 'this' context of type
        'WebElement & Omit<NestedElements<WebElement, { input: WebElement;
         field: (name: string) => any; fill2: (n: string) => Promise<void>; }>,
         "fill2">'
      is not assignable to method's 'this' of type
        '... Omit<..., "field">'.

  Calling a sub-ELEMENT from a method is fine, which is why the README's
  fillForm example works — it only touches this.usernameInput and friends.
  Calling a sibling METHOD is what fails.

  Note the error also shows `field: (name: string) => any` — the sibling's
  return type collapses to `any` inside the mapped type, so even the error
  message loses information.

WHY IT MATTERS
  It is invisible until hit, the error text does not name the actual rule, and
  the workarounds are all bad:
    - annotating `this:` does not help, because the mapped type discards it
      (this cost real time to discover);
    - splitting into `.with()` + `.withMethods()` works, because the second
      stage's `this` contains all of the first — but it doubles the
      declaration shape of every component and contradicts the README, which
      shows one `.with()`;
    - duplicating the sibling's body inline works and is what this suite ended
      up doing.

PROPOSED FIX
  The `Omit<..., K>` exists to avoid a circular type reference. It can be kept
  while still exposing the siblings, by making the self-reference lazy through
  an interface rather than an inlined mapped type:

      type Methods<A> = { [K in keyof A]: A[K] extends (...a: any) => any ? K : never }[keyof A];

      type Nested<T extends WebElement, A> = {
        [K in keyof A]: A[K] extends WebElement
          ? A[K] & Nested<A[K], InferNested<A[K]>>
          : A[K] extends (this: any, ...args: infer Args) => infer R
            ? (this: Self<T, A>, ...args: Args) => R
            : A[K];
      };

      // one named alias, so the reference is deferred instead of expanded
      interface Self<T extends WebElement, A> extends WebElement {
        // structural body supplied by the intersection below
      }
      type SelfOf<T extends WebElement, A> = T & { [K in keyof A]: A[K] };

  In practice the smallest change that fixes it is to type `this` as the
  RESULT type of `with` rather than as a subtraction of the augment:

      with<T extends WebElement, A>(this: T, augment: NestedElements<T, A>): T & A;
      //                                                    ^ methods get `this: T & A`

  i.e. inside NestedElements, replace
      (this: T & Omit<NestedElements<T, A>, K>, ...args: Args) => Result
  with
      (this: T & A, ...args: Args) => Result

  `T & A` is the object `with` returns, which is what `this` actually is at
  run time — the current type is strictly less accurate than reality. TypeScript
  tolerates the reference because A is a type parameter, not an expanded
  mapped type, so the circularity that Omit was working around does not arise.

  Whatever the mechanism, please also:
    - add a type test for the sibling-method case, so it stays fixed;
    - document the limitation in docs/web_element.md if it cannot be fixed,
      including the `.with()` + `.withMethods()` escape hatch, because right
      now nothing in the docs hints at it.

12  MEDIUM — TestId<K> cannot infer K, and the default accepts every brand
================================================================================

WHAT
  builder.d.ts:58

      export declare const sid: <K extends string = string>
        (...parts: Array<string | number>) => TestId<K>;

  K appears only in the RETURN type, so it can never be inferred from
  arguments. Every call without an explicit type argument produces
  TestId<string>. And because the brand property is covariant, TestId<string>
  is the top type of the family: every other brand widens to it.

EVIDENCE
      const loose  = sid("username-input");                       // TestId<string>
      const strict = sid<"login.username">("username-input");
      const other  = sid<"header.logo">("header-logo");

      const a: TestId<string> = strict;   // no error
      const b: TestId<string> = other;    // no error
      const c: TestId<"login.username"> = loose;
      //    error TS2322: Type 'TestId<string>' is not assignable to
      //    type 'TestId<"login.username">'.

  So the protection only exists where the author remembered the type argument,
  and any API that accepts TestId (the default TestId<string>) accepts all of
  them — including testIdProps and $byTestId.

WHY IT MATTERS
  The module's first documented benefit is "Branded types for test IDs to
  prevent misuse", with an example showing ButtonId vs ContainerId not being
  interchangeable. In practice the guarantee holds only for hand-annotated
  declarations, and the README's own `ids` object is the annotated form — so
  the docs show the working case while the ergonomic case silently opts out.

PROPOSED FIX
  Two options, both worth doing:

  (a) Make the brand carry from the FACTORY, where a type argument is natural
      and written once, instead of from every call site:

          const button = factory<'button'>('btn');
          button('submit');   // TestId<'button'> — inferred, no annotation

      This already works for `factory`. The gap is only `sid`. Add a
      namespacing helper so statics get the same treatment in one place:

          export const ns = <K extends string>() =>
            (...parts: Array<string | number>): TestId<K> => sid<K>(...parts);

          const loginId = ns<'login'>();
          export const ids = {
            login: {
              usernameInput: loginId('username-input'),  // TestId<'login'>
              passwordInput: loginId('password-input'),
            },
          } as const;

  (b) Stop TestId<string> from being the universal acceptor by making the
      brand invariant, so widening requires an explicit decision:

          export type TestId<Kind extends string = string> = string & {
            readonly [__testIdBrand]: (k: Kind) => Kind;   // invariant position
          };

      A function type in the brand makes the property neither co- nor
      contravariant, so TestId<'a'> and TestId<string> stop being assignable
      in either direction. Then add one explicit widener for the cases that
      genuinely need it:

          export const anyId = (id: TestId<string>): TestId => id;

      This is a stricter model; whether it suits depends on how much existing
      code passes ids around as TestId. Worth at least documenting the
      current variance so users know what the brand does and does not stop.

  Whichever is chosen, add type tests: TestId<'a'> not assignable to
  TestId<'b'>, and the intended relationship with TestId<string> asserted
  explicitly rather than left to be discovered.

      export function assertNoPrefixCollisions(
        ids: Record<string, unknown>,
      ): void {
        const factories: IdFactory[] = [];
        const statics: string[] = [];
        const walk = (node: unknown) => {
          if (isIdFactory(node)) return void factories.push(node);
          if (typeof node === 'string') return void statics.push(node);
          if (node && typeof node === 'object') Object.values(node).forEach(walk);
        };
        walk(ids);

        const problems: string[] = [];
        for (const f of factories) {
          if (!f.prefix) continue;
          const allowed = new Set(f.aliasPrefixes ?? []);
          for (const s of statics) {
            if (s.startsWith(f.prefix) && s !== f.prefix && !allowed.has(s)) {
              problems.push(`factory '${f.prefix}' also matches static id '${s}'`);
            }
          }
          for (const g of factories) {
            if (g === f || !g.prefix) continue;
            if (g.prefix.startsWith(f.prefix) && !allowed.has(g.prefix)) {
              problems.push(`factory '${f.prefix}' also matches factory '${g.prefix}'`);
            }
          }
        }
        if (problems.length) {
          throw new Error('[playwright-elements] test id prefix collisions:\n  ' +
                          problems.join('\n  '));
        }
      }

16  LOW — sid() and factory(p)('') silently produce empty or colliding ids
================================================================================

WHAT
  `join` (builder.js:19) filters out '' and null/undefined, then joins with
  '-'. That is right for skipping optional parts, but it also means missing
  input produces a plausible-looking id instead of an error.

EVIDENCE
  $ node -e "const {sid,factory,bareFactory}=require('playwright-elements'); ..."
      sid()               ->  ""
      sid("")             ->  ""
      sid("a", null, "b") ->  "a-b"
      factory("btn")("")  ->  "btn"
      factory("")("x")    ->  "x"
      bareFactory()(0)    ->  "0"

WHY IT MATTERS
  - `sid()` / `sid('')` yield `data-testid=""`, and `$byTestId('')` becomes
    `[data-testid=""]`, which matches every element with an empty testid.
  - `factory('btn')('')` yields `"btn"` — identical to the factory's own
    prefix, so a row rendered with a missing key collides with any container
    stamped at the prefix, which is finding 05 from the other direction.
  - `factory('')('x')` yields `"x"`, a factory that produces bare keys, which
    is bareFactory's job and defeats prefix selection.
  - `bareFactory()(0)` yielding `"0"` is correct per its docs, but combined
    with the above it means a falsy entity id produces a valid-looking testid.

PROPOSED FIX

      const assertPart = (v: unknown, what: string): void => {
        if (v === '' || v == null || (typeof v === 'string' && !v.trim()))
          throw new Error(`[playwright-elements] ${what} must be a non-empty string`);
      };

      export const sid = <K extends string = string>(
        ...parts: Array<string | number>
      ): TestId<K> => {
        if (parts.length === 0) throw new Error('[playwright-elements] sid() needs at least one part');
        assertPart(parts[0], 'the first part of sid()');
        return join(parts) as TestId<K>;
      };

      export const factory = <K extends string = string>(prefix: string, opts?) => {
        assertPart(prefix, 'factory() prefix');
        return Object.assign((key: string | number) => {
          assertPart(key, `factory('${prefix}') key`);
          return join([prefix, key]) as TestId<K>;
        }, { prefix, aliasPrefixes: opts?.aliasPrefixes });
      };

  Note bareFactory must keep accepting 0 and other falsy-but-valid entity ids,
  so its check should be `key == null || key === ''` only.

  Throwing is right here rather than returning a sentinel: these are called at
  module load when building the `ids` object, so the failure lands at import
  time with a clear message, long before a selector is built.
